# Отчёты сайтов по расписанию

Во вкладке **Сайты → Отчёты** создайте расписание с названием, сайтами, видом отчёта, частотой и временем проверки. Можно выбрать **Аналитику сайта** или **SEO-аудит**. Используются существующие `SiteIntelAnalyticsServiceInterface::analyze` и `SeoAuditServiceInterface::audit`, а HTML формируется существующими шаблонами `reports.site-intel.analytics` и `reports.site-intel.seo-audit`.

Каждый публичный домен или HTTP/HTTPS URL вводится с новой строки и получает отдельный отчёт. По умолчанию доступны до трёх сайтов в расписании и пять сохранённых расписаний суммарно для обоих видов. Настройки находятся в `config/site_intel_reports.php`.

## Частота и данные

- **Каждый день**, **каждые три дня**, **каждые семь дней**: первый запуск через выбранное число дней в указанное время, затем с той же частотой.
- **Каждый месяц**: первого числа следующего месяца в указанное время, затем первого числа каждого месяца.

Часовой пояс выбирается из списка городов со смещением UTC или кнопкой «Использовать время устройства»; по умолчанию — Москва. Планирование учитывает часовой пояс и переходы летнего времени.

Отчёт сохраняет **состояние сайта на момент фактической проверки**: доступность HTTP, DNS, SSL, WHOIS, технические и контентные сигналы существующих сервисов. Частота расписания задаёт повторные проверки, а не статистику посещений или прирост показателей за прошедшие 1 / 3 / 7 дней или месяц. HTML и JSON содержат запланированное время, фактическое `checkedAt`, вид отчёта и часовой пояс; JSON помечает основу данных как `snapshot_at_check_time`.

После простоя планировщика пропущенные проверки объединяются в один последний наступивший запуск для каждого расписания. Система проверяет сайт сейчас и не создаёт несколько одинаковых текущих снимков под видом исторических данных. Задержка worker также не превращает текущую проверку в данные на запланированную дату.

Можно приостановить, возобновить или удалить расписание. Возобновление назначает новый первый запуск. Удаление прекращает автоматические проверки и сохраняет готовую историю. **Сформировать сейчас** работает и при паузе, создаёт текущую проверку и не сдвигает следующий автоматический запуск.

## Параметры SEO-аудита

SEO-аудит сохраняет выбранный предел обхода **от 3 до 20 страниц**, по умолчанию 8. Тип сайта выбирается из `auto`, `generic`, `media-platform`, `content-site`, `storefront`; `auto` передаёт определение профиля существующему сервису. Вид отчёта, URL, предел обхода и тип сайта фиксируются в записи задания до постановки в очередь и сохраняются при повторных попытках.

Предел обхода относится к основному crawl. Проверки robots.txt, sitemap и выборки URL из sitemap выполняются тем же существующим SEO-сервисом отдельно. Аналитика сайта и SEO-аудит сохраняют свои прежние метрики, оценки и рекомендации.

## История и доступ

Готовые снимки хранятся в БД и доступны владельцу как HTML для просмотра и скачивания, а также JSON. Чтение истории и повторное скачивание не запускают новую сетевую проверку и не зависят от кратковременного `REPORT_SNAPSHOT_TTL_SECONDS`.

Для входа во вкладку достаточно разрешения хотя бы на один вид отчёта. Создание, возобновление, ручной запуск, получение готового документа и доставка проверяют разрешение конкретного вида:

| Вид | Ресурс дневного лимита |
| --- | --- |
| Аналитика сайта | `site-intel.analytics` |
| SEO-аудит | `site-intel.seo-audit` |

Каждое новое формирование по одному сайту расходует одну единицу соответствующего лимита; повторная попытка того же задания не списывает её снова. Неуспешное формирование возвращает списание, если завершилось в тот же день учёта квоты. История показывает только разрешённые виды. При сохранении доступа к одному виду в списке остаются собственные расписания другого вида, чтобы их можно было приостановить или удалить после изменения тарифа. Нужен активный аккаунт с подтверждённой почтой.

Публичный URL проверяется синтаксически при создании. Актуальные DNS-адреса проверяются перед выполнением; приватные и зарезервированные адреса запрещены. Существующие HTTP-клиенты дополнительно проверяют каждый редирект и закрепляют проверенный IP-адрес. URL с учётными данными или явным портом не принимаются.

## Telegram-бот

Привяжите аккаунт на `/settings/telegram`, включите доставку файлов в настройках бота и отправку в Telegram в самом расписании. Готовый HTML автоматически отправляется через существующий outbox с типом `site_intel_report`. Меню **Отчёты сайтов** позволяет вручную повторно получить HTML/JSON; для ручного получения не требуется согласие на автоматическую доставку.

Владелец, разрешение конкретного вида, актуальная привязка и согласие на автоматическую отправку проверяются перед доставкой и повторно после подготовки документа. Ошибка бота не отменяет готовый отчёт на сайте; повторяется уведомление, без нового расчёта и расхода лимита. Для доставки нужен отдельный уже настроенный worker очереди `TELEGRAM_BOT_QUEUE`.

## Очередь и запуск

Примените миграции и соберите клиент/SSR:

```bash
php artisan migrate --force
npm run build
```

SEO выполняет несколько последовательных сетевых запросов, поэтому для сайтов предусмотрены отдельные queue connections с увеличенным временем резервирования задания:

```dotenv
SITE_INTEL_REPORTS_QUEUE_CONNECTION=site-intel-reports-database
SITE_INTEL_REPORTS_QUEUE=site-intel-reports
SITE_INTEL_REPORTS_TIMEZONE=Europe/Moscow
SITE_INTEL_REPORTS_TIMEOUT=900
SITE_INTEL_REPORTS_RETRY_AFTER=960
```

В `config/queue.php` соединения `site-intel-reports-database` и `site-intel-reports-redis` используют соответственно database и Redis. Database-вариант использует общую таблицу `jobs`, но отдельную настройку `retry_after`; стандартные очереди других модулей не меняются. Для Redis задайте `SITE_INTEL_REPORTS_QUEUE_CONNECTION=site-intel-reports-redis` и используйте это же имя в команде worker.

По умолчанию `retry_after` — **960 секунд**, timeout задания — **900 секунд**, lease — **1200 секунд**. `retry_after` и lease должны превышать timeout. Lease задаётся в `site_intel_reports.lease_seconds`, при необходимости через `SITE_INTEL_REPORTS_LEASE_SECONDS`. Обычное соединение `database`/`redis` с `retry_after=150` не подходит для этих длительных проверок. Cache должен поддерживать атомарные блокировки; в production нужен общий постоянный cache.

```bash
php artisan queue:work site-intel-reports-database --queue=site-intel-reports --timeout=900 --tries=1 --sleep=1 --max-time=3600
php artisan schedule:list
```

Worker должен постоянно работать под Supervisor/systemd и перезапускаться после выхода. Согласуйте время штатной остановки Supervisor/systemd с timeout задания. Для локальной проверки можно убрать `--max-time=3600`. Максимум попыток формирования хранится в БД и по умолчанию равен трём; `--tries=1` относится к отдельной доставке задания очередью.

Модуль регистрирует `site-intel:reports-maintain` каждую минуту. Команда создаёт наступившие проверки, восстанавливает незавершённые задания и повторяет уведомления о готовых отчётах. На сервере нужен `php artisan schedule:run` каждую минуту; локально можно использовать `php artisan schedule:work`. Уже настроенный Laravel scheduler обслуживает этот модуль без дополнительного cron.

После изменения конфигурации обновите config cache и перезапустите workers. Готовые снимки при восстановлении очереди не пересчитываются.
