# Отчёты аналитики Telegram по расписанию

Во вкладке **Telegram → Отчёты** пользователь создаёт расписание: название, до трёх публичных групп/каналов, интервал, время и часовой пояс. До пяти расписаний могут храниться одновременно; лимиты задаются в `config/telegram_analytics_reports.php`.

- Каждый день: предыдущий завершённый день.
- Каждые три дня: три предыдущих завершённых дня.
- Каждые семь дней: семь предыдущих завершённых дней.
- Каждый месяц: первого числа, весь предыдущий календарный месяц.

Первый дневной/трёхдневный/недельный запуск происходит через выбранное число дней в заданное время. По умолчанию используется `Europe/Moscow`. Границы периодов фиксируются до постановки в очередь; задержка worker не меняет период. Пропущенные запуски восстанавливаются ограниченными партиями.

Для каждой группы создаётся отдельный отчёт с текущей аналитикой и сравнением с предыдущим периодом, если оно доступно. Готовые данные сохраняются в БД независимо от кратковременного кэша интерактивной аналитики. На сайте доступна история, просмотр HTML и скачивание HTML/JSON. Просмотр и скачивание не обращаются к Telegram и не расходуют лимит аналитики повторно.

Расписание можно приостановить, возобновить или удалить. Возобновление назначает новый первый запуск без восстановления периода паузы. Удаление прекращает автоматическую работу и сохраняет готовую историю. **Сформировать сейчас** создаёт отдельный запуск за предыдущий завершённый период, работает также при паузе и не сдвигает следующий автоматический запуск.

## Бот

Включите «Также отправлять отчёты в Telegram», привяжите аккаунт на `/settings/telegram` и включите доставку отчётов (`exports_enabled`). Бот присылает HTML после успешного формирования; HTML/JSON можно повторно получить через пункт меню аналитических отчётов. Отсутствие связи или выключенная доставка не мешает сохранению на сайте.

Бот получает событие `AnalyticsReportCompleted` через адаптер в `app/Integrations/TelegramBot`. Outbox дедуплицирует доставки по ID отчёта. Ошибка постановки в outbox повторяется без пересчёта аналитики. Права, актуальная связь, настройки доставки и принадлежность отчёта проверяются непосредственно перед отправкой. Доставленные в Telegram копии сохраняются в Telegram независимо от сайта.

## Доступ и обработка

Все HTTP-операции требуют авторизации, подтверждённой почты, незаблокированного аккаунта и доступа к `telegram.analytics`. Готовые отчёты и расписания доступны только владельцу. Каждый новый отчёт по одной группе расходует одну единицу текущего дневного лимита аналитики. Повтор обработки этого же отчёта не списывает лимит снова. Тарифный доступ повторно проверяется при обработке и доставке.

Задание обрабатывает одну группу. Состояния: `pending`, `processing`, `completed`, `failed`; в истории сохраняются безопасные коды ошибок. Очередь и блокировки восстанавливают прерванную обработку. Ошибка Telegram не должна превращаться в успешный отчёт с нулевой активностью. Сбор ограничен существующим `OSINT_TELEGRAM_ANALYTICS_FETCH_MAX_PAGES` и `OSINT_TELEGRAM_ANALYTICS_FETCH_PAGE_LIMIT`; превышение лимита чтения не выдаётся за полный отчёт. Для больших групп увеличивайте эти пределы вместе с ресурсами worker.

## Запуск

Примените миграции и соберите клиент/SSR:

```bash
php artisan migrate --force
npm run build
```

Настройте долговечную очередь:

```dotenv
TELEGRAM_ANALYTICS_REPORTS_QUEUE_CONNECTION=database
TELEGRAM_ANALYTICS_REPORTS_QUEUE=telegram-analytics-reports
TELEGRAM_ANALYTICS_REPORTS_TIMEZONE=Europe/Moscow
```

Используйте `database` или `redis`. `retry_after` должен превышать timeout задания 120 секунд; штатные 150 секунд подходят. В production нужен общий постоянный cache с атомарными блокировками.

```bash
php artisan queue:work database --queue=telegram-analytics-reports --timeout=120 --tries=1 --sleep=1 --max-time=3600
```

Worker должен постоянно работать под Supervisor/systemd с автоматическим перезапуском: `--max-time=3600` завершает процесс через час. Для локальной проверки в терминале можно убрать `--max-time=3600` и оставить процесс работающим.

Существующий Laravel scheduler вызывает `telegram:analytics-reports-maintain` каждую минуту. На сервере должен работать вызов `php artisan schedule:run` каждую минуту; локально можно запустить `php artisan schedule:work`. Проверка регистрации: `php artisan schedule:list`. Сама команда формирует записи периодов и ставит задания в очередь, поэтому запускать её вручную следует только при намерении начать обработку.

Для доставки также нужен существующий worker очереди, указанной в `TELEGRAM_BOT_QUEUE` (`default` по умолчанию, `telegram-bot` в примере [настройки бота](telegram-bot.md)). После изменения конфигурации/кода обновите config cache и перезапустите worker.

Автоматические тесты используют изолированную БД, подмену Telegram gateway/application service и fake транспорта бота. Реальная доставка и доступность Telegram-сессии проверяются после развёртывания.
